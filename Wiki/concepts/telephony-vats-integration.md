# Телефония: взаимодействие samaya и ВАТС

Полный контур интеграции с ВАТС (`pbx-portal` поверх FusionPBX/FreeSWITCH,
сервер x99, мультиарендность по доменам `<org>.vats05.ru`). Номера клиники —
1001–1004 в своей организации; ключ интеграции выпускается в портале
(Интеграции → «Ключи для страницы») и даёт доступ и к API, и к событиям.

## Четыре точки соприкосновения

| Направление | Что | Кто инициирует |
|---|---|---|
| Чтение | журнал звонков, пропущенные, список номеров | samaya (pull, раз в несколько минут) |
| События | звонит / ответили / завершился | ВАТС (push: socket.io или вебхук) |
| Аудио | запись разговора | samaya по требованию оператора |
| Запись в ВАТС | имя сотрудника на номере, отметка «пропущенный обработан» | samaya |

Ключ живёт только в переменных окружения сервиса. Браузер в ВАТС не ходит
никогда: аудио и данные идут через samaya, иначе ключ утечёт на страницу
(документация портала предлагает `?key=` прямо в `<audio src>` — так нельзя).

## Что отдаёт API ВАТС

`https://vats05.ru/api/public`, заголовок `X-Api-Key`.

- `GET /employees` → внутренние номера с именами и состоянием.
- `PUT /employees/:ext {name}` → имя сотрудника на номере: попадает в поле
  `employee_name` всех звонков и на экраны телефонов.
- `GET /calls?from&to&number&employee&direction&limit&offset` → звонки
  (`limit` ≤ 500). Поля: `id`, `at` (UTC), `direction`, `client_number`,
  `client_name`, `line`, `employee` (внутренний номер), `employee_name`,
  `duration` (секунды разговора), `status` (`answered|missed|cancelled`),
  `recording` (путь или `null`).
- `GET /calls/:id` → один звонок.
- `GET /calls/:id/recording` → mp3 (`?format=wav` — исходник).
- `GET /missed?days&open=1` → пропущенные с `attempts`, `handled`, `handled_how`.
- `POST /missed/:id/handled {handled, by, note}` → отметка обработки; видна и в
  портале, и в их Telegram-группе.

События (socket.io комната `events:<домен>` либо вебхук с подписью
`X-Vats-Signature`, HMAC-SHA256 тела секретом вебхука, три попытки доставки):
`incoming`, `accepted`, `ringing` (у кого звонит — есть `employee`), `answered`,
`dialing`, `employee_ended`, `ended` (с `duration`, `hangup_cause`, `recording`).

## Связи сущностей

- **Номер ↔ сотрудник**: таблица связей в samaya. При привязке имя сотрудника
  уходит в ВАТС через `PUT /employees/:ext` — тогда `employee_name` приходит
  готовым и не надо сопоставлять на каждом экране.
- **Звонок ↔ клиент**: по `client_number` против `clients.clients.phone`.
  Номера приводим к `+7XXXXXXXXXX` с обеих сторон — в базе клиентов телефоны
  лежат в разном виде (`89…`, `79…`, с пробелами).
- **Звонок ↔ запись**: звонок считается приведшим к записи, если по этому
  клиенту запись создана в течение часа после разговора. Нужно для отчёта
  «звонки → записи», связь хранится полем на звонке, а не пересчитывается.
- **Звонок ↔ смена**: `salons.master_schedules` даёт окно смены сотрудника;
  звонок попадает в смену, если его начало внутри окна.

## Потоки

### 1. Зеркалирование журнала (pull)

Раз в 2–5 минут: `GET /calls` за последние сутки (окно перекрытия покрывает
дозаполнение записи, которая появляется через ~5 секунд после отбоя), upsert по
`id` в свою таблицу. Первый запуск — проход по всей доступной истории
страницами по 500.

Зеркало, а не проксирование на лету: отчёты по сменам это группировки за месяц,
гонять их через чужой API на каждый показ — медленно и хрупко. Плюс журнал
остаётся живым, когда ВАТС недоступна.

### 2. События живьём (push)

Основной способ — **socket.io-подписка из сервиса samaya**: исходящее
соединение, ничего наружу открывать не надо. Вебхук — резерв (публичный
эндпоинт `/api/telephony/events/vats` с проверкой подписи и идемпотентностью по
`id` события).

События дают то, чего нет в журнале: **кто ответил на входящий**. В CDR
ответивший берётся из `cc_agent` (очередь колл-центра), а у клиники входящие
идут мимо очереди — поэтому `employee` у всех входящих пуст. В событиях же
плечо к сотруднику приходит с `employee`: `ringing` — у кого звонит,
`answered` — кто взял. Эти события пишем сырыми и из них проставляем
ответившего на звонке.

#### Как сделано (2026-09-13)

- `telephony-service/src/events.ts` — socket.io-клиент к порталу (`origin` от
  `VATS_BASE_URL`, `auth.eventKey` = ключ организации), через `VATS_PROXY_URL`
  собственным `https-proxy-agent`: undici-прокси на websocket не действует,
  а egress-мост пропускает `CONNECT` как есть. Каждое событие пишется в
  `call_events` (`ON CONFLICT (id) DO NOTHING` — повтор при переподключении не
  показывает карточку дважды), `answered` проставляет `extension`/`master_id`
  звонку, `ended` через 12 с дёргает синхронизацию журнала.
- `routes/stream.ts` — `GET /api/telephony/stream`, SSE. Кому что: есть
  привязанный номер (`masters.user_id` → `extension_links`) — только свои
  звонки и продолжение уже показанных; нет номера, но owner/admin — все
  входящие (ресепшен); иначе 403 `NO_EXTENSION`. Пинг каждые 20 с, чтобы Kong
  и nginx не закрывали молчащий ответ; в `frontend/nginx.conf` для этого пути
  выключена буферизация.
- Фронт (`app.js`, блок «Всплывающая карточка входящего»): fetch с Bearer
  (EventSource не умеет заголовки), переподключение с экспоненциальной
  паузой, 403 — тихо перестаём. Карточка внизу справа: состояние
  (звонит/разговор/завершён/пропущен), у кого звонит, имя клиента из базы или
  «Новый номер», кнопки «Карточка» / «Создать клиента» (телефон подставлен) и
  «Записать» (телефон подставлен в форму записи). После отбоя карточка живёт
  ещё 90 с: оформить клиента чаще успевают после разговора.
- Отметки по звонку (2026-09-14, `056_telephony_call_marks.sql`, таблица
  `call_marks` — отдельная, потому что строка в `calls` появляется только после
  отбоя и синхронизации, а отметку ставят во время звонка):
  - «Обработано» — `POST /calls/:id/mark {processed:true}`. Сервер убирает
    звонок из `activeCalls`, запоминает его в `handled` и шлёт в поток событие
    `handled` — карточка закрывается у всех администраторов и не всплывает
    снова ни на «звонит» у следующего сотрудника, ни при переподключении SSE
    (раньше повтор идущих звонков новому соединению поднимал её заново).
    Закрытие AI-заявки помечает обработанным и её звонок. Крестик на карточке
    — то же, но только в этом браузере (`callPop.dismissed`).
  - «Кто звонил» — чипы «Клиент/Новый клиент» и «Сотрудник»,
    `{caller_kind}`. «Новый клиент» на незнакомом номере сразу создаёт клиента
    через `POST /api/clients` (имя — подпись номера из ВАТС или «Без имени»),
    дальше кнопка «Карточка». «Сотрудник» запоминается за номером: следующий
    звонок с него приходит уже с `caller_kind`, карточка подписана «Сотрудник»
    без «Создать клиента»; в журнале — бейдж «сотрудник».
- В `GET /api/telephony/status` добавлено `events.connected` — жив ли канал.

### 2а. Звонки, на которые ответил AI-оператор (2026-09-13)

Портал отдаёт `handled_by` (employee / ai / null) в журнале, блок `ai`
(резюме, заявка, расшифровка) в `GET /calls/:id`, список заявок
`GET /tickets` + `POST /tickets/:id/handled` и событие `ai_ticket`.

У нас (`055_telephony_ai.sql`): колонка `calls.handled_by`, таблица
`ai_tickets` — зеркало заявок (PK = id заявки в ВАТС, статус общий).
- `sync.ts` `syncTickets()` — заявки за 7 дней каждым циклом, привязка
  клиента по `phone_digits`; `events.ts` кладёт заявку сразу из `ai_ticket`.
- `routes/tickets.ts`: `GET /api/telephony/tickets?status&days`,
  `POST /tickets/:id/status` (сначала ВАТС, потом своя база — статус не
  расходится), `GET /calls/:id/ai` — резюме и расшифровка по требованию, право
  `telephony.listen`; текст разговора у себя не храним.
- Фронт: вкладка «Телефония → AI-заявки» с бейджем новых, в журнале «Принял»
  = «AI-оператор» (клик — плеер с резюме и расшифровкой под записью), карточка
  «AI-оператор принял заявку» по событию с кнопками «Записать» / «Обработано».

### 3. Прослушивание

`GET /api/telephony/calls/:id/recording` в samaya: сервис тянет mp3 из ВАТС с
ключом, кладёт в файловый кэш и отдаёт браузеру **с поддержкой Range**.

Кэш нужен именно из-за перемотки: портал генерирует mp3 на лету через ffmpeg и
отдаёт chunked, без `Content-Length` и без Range — ползунок в плеере работать не
будет. Скачанный файл эту проблему снимает и заодно убирает повторную
перекодировку при каждом прослушивании.

### 4. Обратная запись в ВАТС

- Привязали сотрудника к номеру → `PUT /employees/:ext {name}`.
- Пропущенный обработан → `POST /missed/:id/handled`. Вручную кнопкой и
  автоматически: если по номеру пропущенного создана запись, отмечаем с
  примечанием «записан на <дата, время>». Администратору не придётся закрывать
  одно и то же дважды в двух системах.

## Модель данных (схема `telephony`)

- `extension_links` — `company_id`, `extension`, `master_id`, имя, отданное в
  ВАТС; уникален `extension` в пределах компании.
- `calls` — зеркало журнала: `id` (uuid из ВАТС, первичный ключ — так upsert
  идемпотентен), время, направление, номер и имя клиента, линия, внутренний
  номер, `master_id`, длительность, статус, признак записи, `client_id`,
  `booking_id`, время синхронизации.
- `call_events` — сырой поток событий: `call_id`, тип, `employee`, время,
  исходный payload. Из него восстанавливается ответивший и разбираются спорные
  случаи.
- `missed_state` — зеркало пропущенных плюс локальные отметки обработки.
- `recording_cache` — путь к файлу, размер, время загрузки; чистится по сроку.
- `sync_state` — курсор синхронизации, время последнего успеха и ошибка.

## Эндпоинты samaya (`/api/telephony`)

- `GET /calls` — журнал с фильтрами (период, сотрудник, направление, статус,
  номер, клиент).
- `GET /calls/:id`, `GET /calls/:id/recording` (Range).
- `GET /missed`, `POST /missed/:id/handled`.
- `GET /extensions`, `PUT /extensions/:ext` — привязка к сотруднику.
- `GET /report/shifts?from&to&master_id` — сотрудник × смена.
- `GET /stream` — SSE для всплывающей карточки звонящего в браузере админа.
- `POST /events/vats` — приём вебхука (резервный путь доставки).

## Экраны

- **Телефония → Журнал**: список звонков, плеер, имя клиента со ссылкой на
  карточку, фильтры.
- **Телефония → Пропущенные**: необработанные сверху, сколько раз звонил,
  кнопки «Перезвонили» / «Записали».
- **Телефония → По сменам**: сотрудник × дата смены — принято, пропущено,
  исходящие, суммарное и среднее время разговора.
- **Телефония → Номера**: привязка 1001–1004 к сотрудникам.
- **Карточка клиента → Звонки**: все разговоры с этим человеком.
- **Всплывающая карточка входящего** у администратора: кто звонит, был ли
  клиентом, кнопки «Открыть карточку» и «Записать».

## Безопасность и персональные данные

- Запись разговора с пациентом — персональные данные и врачебная тайна.
  Прослушивание — отдельное право (`telephony.listen`), каждое прослушивание
  логируется: кто, какой звонок, когда. Журнал звонков — право
  `telephony.view`, привязка номеров — `telephony.manage`.
- Кэш аудио хранится ограниченный срок и не попадает в бэкапы приложения.
- Вебхук без корректной подписи отбрасывается; повторная доставка одного
  события не должна менять состояние дважды.

## Что мешает сейчас и что доработать в портале

1. ~~**Ответивший на входящий**~~ — закрыто 2026-09-13 на стороне портала:
   номер сотрудника прошивается в плечо набора (`api_on_answer` →
   `cc_agent`), `employee` приходит и в журнале, и в событиях. История до
   этой даты остаётся без ответившего.
2. **Range у записи** — сейчас mp3 генерится на лету. Кэш в samaya снимает
   проблему; на стороне портала можно хранить готовый mp3 рядом с wav.
3. **Курсор синхронизации** — фильтры только `from/to/offset`; при росте объёма
   удобнее `updated_since`.
4. **Набор номера из карточки клиента** (click-to-call) — в API его нет, в
   портале есть ESL и вебфон; добавляется отдельным эндпоинтом.

## Порядок работ

1. Зеркало журнала, прослушивание с перемоткой, привязка номеров.
2. События живьём: ответивший на входящих и всплывающая карточка.
3. Пропущенные с отметкой обработки, автоотметка по созданной записи.
4. Отчёт по сменам.
5. Доработки портала из списка выше.
