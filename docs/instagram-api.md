# Instagram Direct: подключение официального API

Как устроен путь от сообщения клиента до ответа и что нужно сделать, чтобы
он заработал на живых клиентах.

## Поток

```
клиент пишет в Direct
   → Meta шлёт webhook на /api/instagram/webhook
   → проверка подписи (INSTAGRAM_APP_SECRET)
   → сообщение в instagram.messages
   → salon-service /api/salons/ai/reply определяет тему (Jev)
   → шаблон отправляется сам ИЛИ ложится черновиком администратору
```

Текст ответа не генерируется: модель выбирает тему, текст берётся из
`ai.reply_templates` дословно.

## Что нужно заполнить

| Где | Что | Зачем |
|---|---|---|
| Настройки → Интеграции | токен доступа | отправка сообщений |
| `.env` | `INSTAGRAM_VERIFY_TOKEN` | любая строка, вы её придумываете сами |
| `.env` | `INSTAGRAM_APP_SECRET` | секрет приложения из кабинета Meta |
| `.env` | `INSTAGRAM_AUTOREPLY=true` | когда готовы отвечать без человека |

`VERIFY_TOKEN` не секрет — это взаимная сверка: одну и ту же строку вы
пишете в `.env` и в кабинет Meta. `APP_SECRET` — настоящий секрет, им
подписываются входящие уведомления; без него эндпоинт принимал бы
выдуманные сообщения от кого угодно, потому что открыт наружу без
авторизации.

## Подключение webhook в кабинете Meta

1. developers.facebook.com → ваше приложение → Products → Webhooks.
2. Объект — **Instagram**, Callback URL:
   `https://клиника-самая.рф/api/instagram/webhook`
3. Verify Token — та же строка, что в `INSTAGRAM_VERIFY_TOKEN`.
4. Подписаться на поле **messages**.

Meta дёрнет GET с проверочным токеном; сервис ответит `hub.challenge`.
Если подключение не проходит — смотрите логи:
`docker compose logs instagram-service | grep webhook`.

## Advanced Access — обязательный шаг для боя

Пока приложение в режиме разработки, webhook доставляет сообщения **только
от людей с ролью в приложении**. Клиентские сообщения не придут.

Это же ограничение ломает чтение списка диалогов: на аккаунте с 228 тысячами
подписчиков запрос `/me/conversations` отваливается по таймауту, и Meta прямо
пишет, что нужен Advanced Access к `instagram_manage_messages`.

### Как подать

App Review → Permissions and Features → `instagram_manage_messages` →
Request Advanced Access.

Понадобится:

- **Описание использования.** По существу: CRM клиники отвечает клиентам на
  типовые вопросы (часы работы, адрес, запись) готовыми шаблонами; вопросы
  о здоровье и жалобы передаются администратору, бот на них не отвечает.
- **Скринкаст.** Показать весь путь: сообщение приходит в Direct →
  появляется в CRM → администратор отвечает или подтверждает черновик.
- **Политика конфиденциальности** на сайте клиники.
- **Verified Business** — у приложения должна быть подтверждённая компания.

Рассмотрение — обычно несколько дней. До одобрения можно всё тестировать:
добавьте свой аккаунт в роли приложения (Roles → Testers), и его сообщения
будут доходить.

## Окно 24 часа

Ответить можно только в течение суток с последнего сообщения клиента —
правило Meta, обойти нельзя. Черновик, пролежавший до утра, не отправится:
сервис вернёт «прошло больше 24 часов с сообщения клиента». Для
автоответов это некритично (они уходят сразу), но администратору стоит
знать, почему вчерашний черновик не уходит.

## Маршруты сети

Два внешних сервиса требуют противоположного, поэтому у них разные мосты:

| Сервис | Мост | Адрес | Почему |
|---|---|---|---|
| Meta | `egress-proxy-vless` (1181) | российский | прямой маршрут до `graph.facebook.com` не резолвится; выход голландским адресом = блокировка аккаунта |
| TypeSafe (Jev) | `egress-proxy` (1180) | голландский | на российский адрес отвечает 451 «not available in your region» |

Проверка одной командой:

```bash
ssh iTTEST 'cd ~/samaya && bash scripts/check-egress.sh'
```

Отдельная ловушка: в окружении контейнеров заданы системные `HTTPS_PROXY` и
`http_proxy`, и undici подхватывает их молча. Поэтому в коде диспетчер
задаётся явно — иначе запрос уходит не туда, куда написано в конфиге.
